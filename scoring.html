How capability scoring works

← back to browser

Each model shows a capability score from 0–100 for the use case you picked. These are indicative rankings, not raw benchmarks: they are only comparable within one axis (a 70 for coding and a 70 for creative do not mean the same thing), and they are meant to answer “which of these will probably serve me best?”, not “what did this model score on test X?”

Each model is scored separately per use case, from public leaderboards where available:

Raw metrics are normalized to 0–100 per axis (rescaled so the weakest rated model sits near 30, not 0). Only vision-capable models appear under the vision axis.

Measured vs. estimated

Scores come from a small curated table keyed to each model’s base model. Because a live trending feed is full of brand-new models and fine-tunes the table hasn’t reached, anything without a match gets an estimate instead of being hidden.

  • Measured – matched to a curated entry sourced from the leaderboards above.
  • Estimated (tagged est.) – no benchmark match, so capability is inferred from total parameter count, recency, a same-family prior (a new Qwen3.x inherits from the best known Qwen entry), domain tags in the name (e.g. “coder”), and a small popularity nudge. Estimates are capped just below the measured ceiling so a genuinely-benchmarked top model always outranks a guess. In the chart they are drawn as hollow dots; the “Show estimated” toggle hides them.

Estimates track total params, so a 30B mixture-of-experts with 3B active is scored like a 30B model (its capability), while its speed is estimated from the 3B it actually runs (see below). A 4B and a 30B in the same family get clearly different scores.

Quantization retention

The score above is for the model at full quality. Each quant then keeps a fraction of it: effective capability = base score × retention(quant). Lower-bit quants lose a little quality:

QuantRetention
F16 / Q8~1.00
Q6_K~0.995
Q5_K~0.99
Q4_K / IQ4_XS~0.97
Q3 / IQ3~0.90
Q2 / IQ2~0.78
IQ1 / TQ~0.60

This is why a big model at Q4 can out-rank a small model at Q8 – the retention curve keeps them comparable. The curve is a heuristic (grounded in perplexity deltas) and tunable.

Speed & footprint

Decode speed (tok/s) is estimated as ~0.8 × memory bandwidth / bytes read per token, where bytes ≈ quant size (× active/total for MoE) plus the KV cache. It is a bandwidth-bound estimate – it ignores prefill and compute, so treat it as an order-of-magnitude guide. Footprint is quant weights + estimated KV cache for your context and KV-cache quant.

The Pareto frontier

For each (model, quant) that fits your VRAM, the tool plots capability against cost (speed and size). A point is on the frontier (green, ★) if nothing else beats it on both at once – the set worth choosing from. The recommended pick (gold) is the frontier point that best matches your capability-vs-speed slider.

Caveats

  • Scores are indicative, not benchmarks; normalization across different leaderboards is inherently fuzzy.
  • Estimated scores for long-tail fine-tunes are rough – use the “est.” tag and the toggle accordingly.
  • tok/s is a decode-only estimate; real throughput depends on backend, prompt length, and attention.
  • A live capability API was considered but rejected on licensing/coverage grounds – see the README for the full sourcing rationale.
