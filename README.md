# HF Hardware Browser

A static site that answers **"what's the best model I can run on my GPU(s)?"** — not
just *which GGUF models fit*, but which are strongest for a given use case, and how
capability trades off against speed and size on a **Pareto frontier**.

Live data is refreshed hourly from the Hugging Face API and deployed to GitHub Pages.

## What it does

1. Pick up to 4 GPUs, a context length, and a KV-cache quant. VRAM + aggregate memory
   bandwidth are computed for you.
2. Pick a **use case**: coding, general/chat, reasoning/math, multimodal (vision),
   agentic/tool-use, creative, or long-context.
3. Every **(model, quant)** combination that fits your VRAM is scored on two axes:
   - **capability** for the chosen use case (see below), and
   - **cost** — estimated decode speed (tok/s) *and* total footprint (GB).
4. The **Pareto frontier** (non-dominated set) is highlighted, a recommended pick is
   surfaced (with a capability↔speed weight slider), and results are shown as an
   interactive **chart** or a re-sorted **list**.

## Architecture

- `update_models.py` — hourly job. Pulls trending GGUF repos from the HF API, groups
  files into quant types with total sizes, and (via each repo's `base_model:` tag) reads
  the base model's `config.json` for attention shape. Also records `base_model`,
  `params_b` (+ MoE `params_active_b` when derivable), `modalities`, and
  `has_vision_projector`. Writes `data/models.json`, `data/gpus.json`,
  `data/metadata.json`.
- `data/capabilities.json` — **curated** capability table (see below). Committed and
  human-reviewed; **not** regenerated by the hourly job.
- `index.html` — the whole app. Loads the JSON, joins models to capability entries by
  base-model id, applies the quant-retention curve, estimates tok/s, computes the
  frontier, and renders. No build step, no runtime dependencies.
- `.github/workflows/update-and-deploy.yml` — runs the updater hourly, commits
  `data/*.json`, and deploys `index.html` + `data/*` (including `capabilities.json`) to
  GitHub Pages.

## The capability table (`data/capabilities.json`)

### Why curated + fallback (and not a live API)

We evaluated automated capability feeds. The only broad, fresh, blended source with a
real API is **Artificial Analysis**, whose terms forbid republishing its scores (and
we'd be committing them into a public repo). The free alternatives are each blocked in
some way: OpenRouter and LMArena ban scraping/redistribution, the Open LLM Leaderboard
is retired and frozen, llm-stats has no real benchmark API, and the rest (Aider,
OpenVLM, LiveBench) are narrow slices or stale. So this tool uses a **free, curated
table + a heuristic fallback** rather than a paid or scraped live feed. See below.

Curated because a live leaderboard scrape is brittle (names change, sources disappear,
fuzzy matching to arbitrary GGUF repos fails). Each entry is keyed on a canonical HF
base-model id plus `aliases` used for matching, and carries per-axis scores:

```json
{
  "base_model": "Qwen/Qwen3-Coder-30B-A3B-Instruct",
  "aliases": ["Qwen3-Coder-30B-A3B-Instruct", "Qwen3-Coder-30B"],
  "params_b": 30.5, "params_active_b": 3.3,
  "modalities": ["text"],
  "scores": { "coding": 84, "general": 68, "reasoning": 62,
              "vision": null, "agentic": 74, "creative": 58, "longctx": 78 },
  "sources": { "coding": "aider-polyglot", "agentic": "bfcl-v3" }
}
```

- **Scores are normalized 0–100 per axis** and are *indicative, not raw benchmarks* —
  comparable within an axis only. `null` means the model was not evaluated on that axis
  (it is excluded from that axis's frontier; e.g. text-only models get `vision: null`).
- **Provenance** per axis in `sources`. Seed leaderboards: coding = Aider polyglot /
  BigCodeBench; general = LMArena (open-weights Elo); reasoning = GPQA-Diamond /
  MMLU-Pro / MATH; vision = MMMU / OpenVLM; agentic = BFCL; creative = EQ-Bench;
  long-context = RULER.

### Matching models to entries

A GGUF repo (e.g. `bartowski/Qwen3-Coder-30B-A3B-Instruct-GGUF`) is matched to a
capability entry by, in order: its `base_model` id → normalized alias exact match →
normalized substring match of the repo id against an alias (length-guarded). Repos with
no match, or a `null` score on the active axis, are shown in a separate **"unrated"**
section rather than dropped.

### Refreshing capability scores

The table is maintained by hand from the leaderboards above. To (re)gather the raw rows
mechanically, run the leaderboards through a batch of small-model research agents (one
per source), normalize each axis 0–100, and merge into `models[]` with provenance. Keep
it human-reviewed — do not wire a live scrape into the hourly job.

## Scoring model (client-side, in `index.html`)

- **Effective capability** = `base_score(axis) × quant_retention(quant)`. The retention
  curve (a tunable lookup) discounts capability by quant precision — roughly F16/Q8 ≈
  1.0, Q6_K ≈ 0.995, Q4_K ≈ 0.975, IQ4_XS ≈ 0.965, Q3 ≈ 0.90, Q2 ≈ 0.80, IQ1/TQ ≈ 0.6.
  This is what makes "big model @ low quant vs small model @ high quant" comparable.
- **Decode tok/s (estimate)** = `0.8 × effective_bandwidth / (weight_bytes×moe_factor +
  KV_bytes)`. `moe_factor = active_params / total_params` for MoE models (only active
  experts are read per token). This is a **decode-only estimate**: it ignores prefill,
  compute, and attention cost, and multi-GPU bandwidth is aggregated optimistically
  (0.65×). Treat it as an order-of-magnitude guide.
- **Footprint** = quant weight size + estimated KV cache (from the base model's attention
  shape and the selected context + KV quant).
- **Heuristic fallback** — models with no benchmark match get an *estimated* capability
  from size baseline + recency + same-family prior + domain-tag hints + a small
  popularity nudge (capped below the measured ceiling so measured top models keep their
  edge). Estimates compete on the frontier but are tagged "est." (dimmed bar in the list,
  hollow dots in the chart); a "Show estimated" toggle hides them. This is what keeps the
  ranking useful for brand-new / fine-tuned models the curated table hasn't reached yet.

UI state (GPUs, context, use case, view, etc.) persists across reloads via localStorage.

## Development

```sh
pip install -r requirements.txt
export HF_TOKEN=hf_...          # required by update_models.py
python3 update_models.py        # regenerates data/models.json etc.
python3 -m http.server 8000     # then open http://localhost:8000
```

`capabilities.json` is edited by hand; `update_models.py` does not touch it.
